Single-Agent with Skills vs. Multi-Agent Systems: What the Research Shows

Why a single agent with the right skills might be all you need—and when it isn't

"Multi-agent" has become the default answer to every complex AI problem. Research assistant? Spin up a crew. Workflow automation? Deploy an agent swarm.

But what if this complexity is unnecessary? A recent paper by Xiaoxiao Li, "When Single-Agent with Skills Replace Multi-Agent Systems and When They Fail", suggests it often is.

The Core Insight: Skills as Internalized Agents

Instead of this:

MULTI-AGENT SYSTEM

Research Agent → Writing Agent → Review Agent

Each with separate context: Context A | Context B | Context C

  • 3 separate contexts (token duplication)
  • Coordination overhead
  • Complex failure modes

The research proposes this:

SINGLE-AGENT WITH SKILLS

One Agent with Skills: research, write, review

↓

Single Context

  • One unified context
  • Direct skill invocation
  • Simple debugging

Skills become internalized agent behaviors within a single context

The result: substantially reduced token usage and latency while maintaining competitive accuracy.

The Phase Transition Problem

Single-agent works beautifully... until it suddenly doesn't.

The research found a phase transition: skill selection accuracy stays stable up to a critical library size, then drops sharply. No gradual degradation—just a cliff.

Skill Selection Accuracy vs. Library Size

5-15 skills: ~100% accuracy (Stable Zone)

15-20 skills: Sharp drop to ~50%

20+ skills: Continued degradation (Breakdown Zone)

Performance remains stable until hitting a critical threshold

The Real Culprit: Semantic Similarity

The breakdown isn't purely about library size—it's about semantic similarity.

# This skill library will fail early:
skills = [
    "write_technical_doc",
    "write_documentation",
    "create_technical_content",
    "author_doc_page"
]
# Too similar → agent confusion

# This library can scale further:
skills = [
    "write_code",
    "run_tests",
    "search_web",
    "analyze_data"
]
# Semantically distinct → clear selection

Skill hygiene matters as much as skill count.

Practical Implications

1. Default to Single-Agent First

# Before:
def solve_problem(task):
    research_agent = Agent("researcher")
    writing_agent = Agent("writer")
    review_agent = Agent("reviewer")
    return orchestrate([research_agent, writing_agent, review_agent], task)

# After:
def solve_problem(task):
    agent = Agent(skills=["research", "write", "review"])
    return agent.execute(task)

2. Watch for Warning Signs

  • Agent picking "close but wrong" skills
  • Adding elaborate prompts to help skill selection
  • Accuracy dropping on skill-dependent tasks

3. Use Hierarchical Organization at Scale

# Instead of 50 flat skills:
skills = ["skill_1", "skill_2", ... "skill_50"]

# Organize hierarchically:
skill_categories = {
    "writing": ["blog_post", "documentation", "email"],
    "analysis": ["data_analysis", "code_review", "research"],
    "code": ["python", "javascript", "sql"]
}

# Agent selects category first, then specific skill

4. When Multi-Agent Still Makes Sense

  • Truly parallel workloads: Tasks that can execute simultaneously
  • Different models needed: GPT-4 for reasoning, Claude for writing
  • Isolation requirements: Hard boundaries between workflow parts
  • Different oversight levels: Some agents need human approval

Why I'm Bullish on Single-Agent

Multi-agent enthusiasm has been driven by impressive demos, not production success. The coordination complexity is real:

Multi-Agent Failure Debugging: "Something went wrong"

  • Which agent failed?
  • What was the state at handoff?
  • Did Agent B receive what Agent A sent?
  • Where's the context from 3 agents ago?

Single-Agent Failure Debugging: "Something went wrong"

  • Check the one context
  • Follow the one decision trace
  • Done

The cognitive science parallel is compelling: humans don't spawn sub-processes to think. We develop skills and apply them from a unified mind. Why should LLMs be different?

Prediction: We'll see a "simplification wave" in agent architectures. Teams will discover simpler approaches work better and are dramatically easier to maintain.

The Bottom Line

Before your next agent project, ask: "Could a single agent with the right skills handle this?"

The research suggests for most use cases, yes. You'll get lower token costs, reduced latency, simpler debugging, and more predictable behavior.

That's not a bad trade for letting go of architectural complexity.
